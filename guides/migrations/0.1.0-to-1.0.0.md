# Migrate from 0.1.0 to 1.0.0

## Breaking changes

- The `approved:` frontmatter key is removed from consumer product documents. Approval records now live in the consumer repository's `docs/approvals.json`; `state` and `revision` remain in frontmatter.
- `check_doc_status` JSON metadata changes to `{path, type, state, revision, approval: {gate, by, date, valid}}`. Update callers that read the former frontmatter approval field to read `approval` instead.
- Technical designs (TDDs) and implementation plans are agent-gated, not developer-gated. The roadmap has no approval gate.
- The implementation orchestrator reports decisions, blockers, and completion to its caller rather than asking the developer directly. Update callers to present developer requests and obtain validation themselves.

The [document contracts](../product-documentation-process.md#document-contracts) own the document formats, [approvals](../product-documentation-process.md#approvals) own approval validity and authority, and [implementation execution](../product-documentation-process.md#implementation-execution) owns the caller's responsibilities.

## Before you start

Use the 1.0.0 Playbook in the consumer repository. Run the steps below from that repository's root, not from the Playbook installation. In command examples, replace `<playbook>` with the path to that installation.

Keep an inventory of the old dates until migration is complete. An old `approved:` date is migration evidence, not permission for an agent to record a developer approval. Do not copy legacy dates into the approvals file by hand or invoke its developer-approval CLI mode as an agent.

## Migration steps

1. **Find product documents with `approved:` frontmatter.** Inspect the consumer's product vision, architecture, roadmap, PRDs, system designs, TDDs, and implementation plans. Search for `approved:` and distinguish frontmatter keys from examples in document bodies. For each product-document frontmatter key, retain the repository-relative path, document type, state, revision (if present), and old date in your migration inventory. Preserve the body, lifecycle state, and revision unless the developer requests a separate change.

2. **Create the approvals file.** Call `doc_approval` in `init` mode for the consumer repository, or run:

   ```sh
   python3 <playbook>/scripts/doc-approval.py --init --repo .
   ```

   This creates `docs/approvals.json` and opts the repository into factory enforcement. Initialization leaves an existing file unchanged; do not replace existing records. Until migration finishes, missing approvals or legacy frontmatter can prevent normal factory work.

3. **Obtain developer confirmations for developer-gated documents.** For each product vision, architecture, PRD, or system design with an old approval, present its path and legacy date to the developer using the [gate request](../communication-policy.md#gate-requests) procedure. Ask the developer to confirm the current document through:

   ```text
   /playbook-approve <path>
   ```

   The developer runs this command in the main OMP session; the agent must not run it or record the approval on the developer's behalf. The command records the current content and confirmation date, not a backdated approval. If confirmation is withheld or changes are requested, leave that gate unresolved and follow the owning review and gate procedures. Do not treat the legacy date as confirmation.

4. **Record agent acceptances for TDDs and implementation plans.** For each active TDD or plan with an old date, call `doc_approval` in `accept` mode with its repository-relative path and evidence `migrated from approved: <date>`, replacing `<date>` with the inventory's date. The CLI fallback is:

   ```sh
   python3 <playbook>/scripts/doc-approval.py --accept --repo . \
     --path docs/features/example/tdd.md \
     --evidence 'migrated from approved: 2026-09-30'
   ```

   Apply the same migration to delivered (`done`) TDDs and plans with legacy approvals, since they also require valid acceptance records. Do not invent an acceptance for a document without a legacy approval: use the [review loop](../document-review.md#review-loop) and normal checks instead. Draft or superseded documents do not need an acceptance to remain in those states. Never use agent acceptance for a developer-gated document.

5. **Drop the roadmap date and remove legacy keys.** The roadmap's date is simply discarded; do not create an approval record for it. Remove the `approved:` frontmatter line from every inventoried document, including drafts and superseded documents. Keep their other frontmatter and bodies intact.

   The preceding order retains the legacy dates while approvals are recorded. Removing the frontmatter key before recording approvals is also safe if you retain the inventory: approval hashes cover only the body after frontmatter, so removing `approved:` does not change the hash. Do not edit the body between approval and the final check; body changes invalidate the recorded approval. Revision changes also invalidate it.

6. **Check every migrated document.** Run `check_doc_status` in `check` mode with each migrated document's path. If the tool is unavailable, run the checker from the consumer root for each path:

   ```sh
   python3 <playbook>/scripts/check-doc-status.py --check docs/product-vision.md
   ```

   Use `check_doc_status` in `json` mode to inspect the new metadata shape when updating a caller. Resolve remaining legacy-key, missing-approval, hash-mismatch, or revision-mismatch diagnostics through the appropriate approval or review procedure; do not change lifecycle states merely to silence a diagnostic.

Migration is complete when all legacy frontmatter keys in consumer product documents are removed, every active or done gated document has a valid record, and every migrated document passes `check_doc_status`. Keep `docs/approvals.json` with the consumer's governing documents. Resume factory work only after unresolved developer gates have been confirmed.
